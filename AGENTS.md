# Автоматизация «ТЗ → OpenAPI»

## Контекст

- **Проект:** корпоративный портал и интеграции (учебный/рабочий кейс)
- **Роль:** PHP / 1C-Bitrix разработчик (модули, REST, HL-блоки, очереди, внешние интеграции)
- **Задача:** из файла ТЗ быстро получать черновик `openapi.yaml` для согласования с backend/mobile/analytics

## Как пользоваться

**Подробная инструкция:** `README.md`

### Файлы `.docx` / `.pdf`

AI-агент не читает бинарные форматы напрямую. Сначала конвертация:

```powershell
python scripts/docx-to-md.py "input/my-spec.docx"
python scripts/pdf-to-md.py "input/my-spec.pdf"
```

Дальше работай с полученным `.md` (то же имя, расширение `.md`).

### Запуск пайплайна

```
/tz-to-openapi @input/my-spec.md
```

или:

```
Проанализируй @input/my-spec.md и сгенерируй OpenAPI по шаблонам проекта
```

**На выходе** в `output/`:
- `{имя}-analysis.md` — разбор ТЗ по чек-листу
- `{имя}-openapi.yaml` — спецификация OpenAPI 3.0.3

## Пайплайн (обязательный порядок)

1. Прочитать `templates/tz-extraction-checklist.md`
2. Суб-агент **tz-analyst** → `output/*-analysis.md`
3. Промежуточный документ по `templates/service-spec-template.md`
4. Суб-агент **openapi-architect** → `output/*-openapi.yaml` на базе `templates/openapi-base.yaml` (без `components`)
5. **Обязательная сверка полноты** → секция `Coverage Audit` в analysis + отчёт пользователю
6. Самопроверка: каждый пункт ТЗ отражён; ничего лишнего не добавлено

## Правила полноты

**Ты — транскрибатор и структуризатор, не автор ТЗ.**

### Запрещено

- Допридумывать endpoints, поля, статусы, auth, коды ошибок, бизнес-правила
- «Улучшать» API от себя (переименовывать ресурсы, добавлять CRUD «для полноты»)
- Заполнять пробелы догадками вместо `TODO: не указано в ТЗ`
- Терять пункты при «красивом» форматировании (таблицы, OpenAPI, summary)

### Обязательно

- Каждый endpoint, поле, enum, правило, ограничение из ТЗ — явно в analysis
- Если в ТЗ неясно — **только** `TODO`, без предположений
- Перед финалом — **Coverage Audit**: пройти исходный ТЗ построчно/посекционно и отметить «учтено / не учтено / TODO»
- OpenAPI содержит **только** то, что есть в analysis, а analysis — **только** из ТЗ
- При расхождении имён/path — **как в ТЗ**, не «как принято в REST»

### Формулировка для самопроверки

> «Могу ли я для каждого элемента в output указать точную цитату или раздел исходного ТЗ?»
> Если нет — элемент лишний, его нужно убрать.

## Стандарты API (Bitrix / корпоративные интеграции)

- **OpenAPI:** 3.0.3
- **REST:** ресурсы во множественном числе, kebab-case (`/policy-applications`)
- **Версионирование:** `/api/v1/...`
- **Auth:** Bearer JWT, Basic или apiKey — по ТЗ
- **Даты:** ISO 8601
- **Ошибки:** `{ "error": { "code", "message", "details" } }`
- **Пагинация:** `limit` + `offset` (или как в ТЗ)

## Инструменты

- **Только Python** — конвертеры в `scripts/`, stdlib где возможно
- Не запускать ruby, npm, npx, yq и прочие CLI для валидации OpenAPI

## Что НЕ делать

- Не выдумывать и не дополнять от себя — см. «Правила полноты»
- Не коммитить prod URL, токены, ПДн
- Не менять смысл требований ради «красивого» API
- Не добавлять секцию `components` в OpenAPI — схемы inline в `paths`
